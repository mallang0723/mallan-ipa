# Marinara iOS v1 — Goal 실행 계약

**버전:** 1.1 · **기준일:** 2026-10-07  
**설계·근거:** [MARINARA_IOS_HANDOFF.md](MARINARA_IOS_HANDOFF.md)  
**개발 지시:** [ASTRA_REQUEST.md](ASTRA_REQUEST.md) · **진행 기록:** [WORKLOG.md](WORKLOG.md)

> 목적은 계획서를 완성하는 것이 아니라, iPhone 안에서 실제 Marinara 엔진과 확장이 돌아가는 첫 버전을 만드는 것이다. 짧게 계획하고 코드로 진행한다.

## 0. Goal을 실제로 시작하기

**✅ Verified — 기능 설명:** Codex의 Goal은 작업 스레드에 유지되는 목표다. `/goal <목표>`로 등록하고, `/goal`로 상태를 확인한다. `/goal pause`, `/goal resume`, `/goal clear`로 제어할 수 있다. [G01]

**이 문서는 Goal 등록 내용을 정의한 일반 Markdown 파일이다.** 파일을 저장소에 넣는 것만으로 Goal이 활성화되지는 않는다. Goal을 지원하는 작업 세션에서 아래 명령을 사용한다. 이것은 Codex 입력창에 넣는 명령이며 터미널의 셸 명령이 아니다.

```text
/goal docs/ios/GOAL.md를 실행 계약으로 사용해 Marinara iOS v1을 구현해. docs/ios/ASTRA_REQUEST.md의 작업 지침과 docs/ios/MARINARA_IOS_HANDOFF.md의 설계·근거를 따르고, docs/ios/WORKLOG.md에서 현재 상태를 이어받아. 문서나 첫 PR만 만들고 완료하지 말고 실제 엔진·채팅·저장·대표 공식 에이전트·Browser 및 Full-page 확장을 연결해. 확인은 변경한 실제 사용 흐름에 한정해. Xcode·서명·실기기·허용된 API 연결이 없으면 독립적으로 가능한 코드를 먼저 마친 뒤 남은 환경 작업을 기록하고, 전체 Goal을 완료로 표시하지 마.
```

앱에서 자연어로 지시할 때는 `ASTRA_REQUEST.md`의 첫 요청문을 사용한다. 실제 제공된 Goal 등록 수단이 있으면 사용하고, 없다면 등록한 척하지 않는다. 존재하지 않는 Goal 도구명·설정 파일·API를 만들지 않는다.

Goal 기능의 활성화 여부는 실행 세션의 결과로 확인한다. **아래 단계·완료 조건은 이 프로젝트의 작업 규칙이지, 새로운 Codex 상태값이나 API 스키마가 아니다.**

## 1. 지속 목표

**Swift 호스트와 WKWebView에 Node.js 런타임 및 기존 Marinara 서버·클라이언트를 내장하여, 별도 Marinara 서버 없이 iPhone에서 채팅·저장·대표 공식 에이전트·브라우저 확장을 사용할 수 있는 개인용 v1을 구현한다.**

모델 생성은 사용자가 설정한 외부 API를 이용한다. 모델까지 iPhone에서 오프라인 실행하는 프로젝트로 확대하지 않는다.

첫 중간 결과물은 **호스트 + 실제 엔진 부팅 코드**다. 이것을 전달해도 전체 Goal은 완료가 아니다. 범위 안의 다음 구현을 계속한다. 매 단계마다 새 계획서나 승인 요청을 만들 필요는 없다.

## 2. 완료 조건 — 실제 쓰는 다섯 흐름

| 완료 조건 | 최소한 남길 결과 |
|---|---|
| 실제 앱과 채팅 | iPhone에서 Marinara 화면을 열고 허용된 API로 대화·스트리밍·중지를 사용한 결과 |
| 파일과 저장 | 캐릭터 PNG/JSON 가져오기, 대화 저장, 앱 완전 종료·재실행 후 데이터 유지, 파일 내보내기 결과 |
| 공식 에이전트 | 대표 정의형 에이전트 하나의 결과 반영 + Tic-Tac-Toe 같은 서버/클라이언트 패키지 하나의 설치·실행 결과 |
| 브라우저 확장 | Browser 및 명시적으로 승인한 Full-page 확장 각각 하나의 가져오기·실행·비활성화, 수정 코드 재승인 결과 |
| 개인용 전달 | 실제 Xcode 프로젝트·연결 코드·빌드 스크립트·빌드/서명/설치 안내, 지원/미지원 목록과 기본 오류 처리 결과 |

기본 오류 처리는 잘못된 키·연결 끊김·저장 실패처럼 실제 만난 경로를 우선 고친다. 기존 변조 파일 거부와 승인 검사를 보존하고 관련 코드 변경 시 해당 검사만 확인한다. 별도 보안 감사 프로젝트를 만들라는 뜻이 아니다.

**39개 에이전트나 모든 API 공급자의 전수 호환은 완료 조건이 아니다.** 그룹 대화·Roleplay·기본 Game 등 원본 핵심 기능은 보존하되, 새 호환 문제는 필수 흐름을 막는지 판단하여 처리하거나 미지원으로 기록한다. 개별 고급 기능 문제를 이유로 첫 실행본 전달을 미루지 않는다. 다만 위 표의 필수 흐름 자체를 미지원으로 남기고 전체 성공을 선언하지 않는다.

소스만 작성됨, 시뮬레이터에서 실행됨, iPhone에서 실행됨을 구분한다. 서명된 IPA를 만들지 않았다면 만들었다고 쓰지 않는다. iPhone 실행 또는 허용된 실제 API 호출이 불가능한 상태는 **구현 진척**이지 전체 Goal 달성은 아니다.

## 3. 작업 순서

**호스트 → 실제 엔진 → 채팅·저장·파일 → 공식 에이전트 → 브라우저 확장 → 개인용 실행본** 순서로 연결한다.

처음에는 저장소 지침·기존 변경·사용 가능한 개발 환경만 확인한다. 이후 필요한 코드 위치를 읽고 수정한다. `console.log()`나 정적 화면만 되는 단계에 머물지 않는다. 반대로 모든 라이브러리의 사전 호환성 표부터 만들지 않는다.

한 묶음마다 코드를 작성하고 해당 경로를 한 번 확인한 뒤, `WORKLOG.md`에 결과와 다음 코드 작업을 짧게 남긴다. 문제가 없으면 다음 묶음을 계속한다. 실패하면 오류와 연결된 최소 경계를 수정한다. **입력이나 코드가 바뀌지 않은 같은 실패를 반복 실행하지 않는다.**

## 4. 반드시 유지할 경계

기존 React/Fastify/파일 기반 저장소와 공식 패키지 설치·로더를 재사용한다. Rust 전체 재작성, 새 DB, 새 범용 플러그인 플랫폼을 도입하지 않는다. `server.mjs` 공식 패키지와 개인용 Server Extension은 다른 실행 경로이므로 전자를 일괄 차단하지 않는다. 기술 근거는 핸드아웃 1장·8장에 있다.

앱 프로세스당 Node 한 번 시작을 기본으로 한다. 필요한 경우 사용자가 앱을 완전히 종료하고 다시 여는 방식으로 처리한다. 상시 백그라운드 실행이나 자동 Node 재기동을 성공 조건으로 추가하지 않는다.

사용자 변경·실제 데이터·저장 형식을 보존한다. loopback 바인딩, 인증, 출처/CSRF, TLS, 원본의 패키지 해시 및 확장 승인 검사를 해제하지 않는다. API 키와 서명 자료를 커밋하지 않는다. 유료 API 호출은 허용된 범위 안에서만 한다.

사용자가 지정한 작업 저장소와 브랜치에서 진행한다. upstream 직접 푸시, 강제 푸시, 보호 브랜치 병합, 배포, 유료 리소스 생성 권한을 이 Goal이 자동으로 부여하지 않는다. 기존 승인·권한·예산 제한을 따른다.

**v1 제외:** 개인용 Server Extension의 OS 샌드박스 포팅, Python/MLX/로컬 모델 sidecar, 로컬 ONNX 임베딩, Professor Mari 셸·워크스페이스 실행, Calls, 외부 장치, 멀티플레이, 엔진 OTA, App Store 제출. Noodle·Slurp·Gacha Forge·World Maps 전체 지원도 필수 조건이 아니다.

## 5. 구현을 멈추지 않는 확인 방식

테스트는 별도 산출물이 아니라 방금 연결한 기능이 되는지 보는 수단이다. 기존 테스트와 작은 수동 확인을 우선 사용한다. 로그에는 실행한 명령·결과·핵심 오류만 남긴다. 통과한 경로는 관련 코드나 실행 조건을 바꿨을 때 다시 본다.

전체 저장소 감사, 전 기능 전수 테스트, 별도 증거 관리 시스템, 각 에이전트별 긴 보고서, 목표와 무관한 리팩터링은 만들지 않는다. 문서만 바뀌었는데 전체 앱 테스트를 반복하지 않는다. 이미 출처를 고정한 설계 근거는 실제 충돌을 발견하거나 기준 버전을 바꿀 때만 다시 확인한다.

## 6. 환경이 없거나 막혔을 때

Xcode·기기·인증서·API 키 하나가 없다는 이유로 다른 구현까지 즉시 멈추지 않는다. 가능한 호스트 코드, 서버 진입점, 빌드 자산 처리, 파일 연결, 플랫폼 분기, 관련 테스트와 실행 안내를 먼저 진행한다. 실제 실행이 필요한 부분만 남긴다.

필수 실행을 더 진행할 수 없고 독립적인 구현도 소진되면, **미완료 상태와 필요한 외부 입력을 기록하고 사용자에게 넘긴다.** 이는 전체 Goal 달성으로 처리하지 않는다. 허위 빌드 로그, 빈 스텁, 실행하지 않은 테스트로 완료 조건을 채우지 않는다.

권한·사용자 중단·예산 제한을 만나면 그 경계를 따른다. 임의로 예산을 늘리거나 우회하지 않는다. 막힌 상태를 표현하려고 지원되지 않는 Goal 상태값을 제출하지 않는다. 실제 환경이 제공하는 상태 전이만 사용하고, 상세 차단 사유는 WORKLOG에 남긴다.

## 7. 기록·재개·종료

중간 보고는 **바꾼 코드 / 실행 결과 / 막힌 점 / 다음 작업**이면 충분하다. 각 턴마다 설계나 출처를 전부 재출력하지 않는다. 중요한 결정 또는 실제 실패가 있을 때만 가정·확인·결과를 한 줄 추가한다.

같은 작업 스레드의 Goal이 일시 중지되었다면 사용자가 `/goal resume`으로 재개할 수 있다. 새 스레드에서는 위 시작 명령으로 목표를 등록하고 기존 `WORKLOG.md`와 현재 diff부터 읽는다. `/goal resume`이 다른 스레드의 목표를 가져온다고 가정하지 않는다. [G01]

완료 조건을 실제로 충족하면 작업 결과를 전달하고, 환경에 제공된 정식 수단으로 Goal 완료를 처리한다. 지원되지 않는 도구 호출을 지어내지 않는다. 환경 차단·예산 종료는 성공과 별도로 보고한다. 완료 후 후속 v1.1 기능을 자동으로 추가하지 않는다.

**현실 경계 기록:** 이 문서 제작 시점에는 Goal용 지시문만 준비했다. 실제 작업 세션에 Goal을 등록하지 않았고 앱 구현·빌드·기기 실행도 하지 않았다. 기존 설계·근거는 유지했다.
