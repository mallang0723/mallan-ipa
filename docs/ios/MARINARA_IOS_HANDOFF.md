# 마리나라 iOS 포팅 — 개발 인계 핸드아웃

**문서 버전:** 1.1 · **기준일:** 2026-10-07  
**용도:** 아스트라(Astra)의 GitHub 개발 착수 / 사용자의 독립 구현 / 두 구현의 비교·참조  
**현재 상태:** 설계 및 소스 조사 완료. iOS 앱 구현·컴파일·실기기 실행은 아직 수행하지 않았다.

> **만들 제품:** 아이폰(iPhone) 앱 안에 노드제이에스(Node.js)와 마리나라 엔진(Marinara Engine)을 넣어, 별도의 마리나라 서버 없이 채팅·역할극·공식 에이전트·브라우저 확장을 사용하는 개인용 앱.
>
> **진행 원칙:** 먼저 돌아가는 앱을 만든다. 검증을 위한 별도 시스템이나 문서를 먼저 만들지 않는다. 부팅, 채팅 저장, 확장 실행, 재실행에서 실제로 문제가 생기는 지점만 확인하고 고친다.

## 0. 읽는 순서와 결정 요약

아스트라는 `ASTRA_REQUEST.md`로 작업을 시작하고, `GOAL.md`를 지속 목표의 완료·중단 조건으로, 이 문서를 설계·근거로 사용한다. `WORKLOG.md`에는 완료 여부와 막힌 점만 기록한다.

**Goal 사용:** 이 폴더의 파일을 저장소에 넣은 뒤 `GOAL.md`의 시작 명령 또는 `ASTRA_REQUEST.md`의 자연어 요청으로 실제 작업 세션에 목표를 등록한다. 문서 배치만으로 활성화되지는 않는다. 첫 PR은 중간 전달 단위이지 전체 Goal 완료가 아니다. Xcode·서명·기기 등 환경이 없으면 가능한 코드를 먼저 마치고, 남은 실기기 작업은 미완료로 기록한다. 기능 사용 근거는 `GOAL.md`의 [G01]을 참조한다.

**1.1 변경:** Goal 실행 계약과 재개 지침을 추가했다. 아래 설계, 기준 커밋, 지원 범위는 유지했으며 iOS 실행 성공으로 상태를 바꾸지 않았다.

1. **기존 코드 재사용:** React 화면과 Node/Fastify 서버를 유지한다. Rust·Swift로 전체를 재작성하지 않는다.
2. **앱 안에서 실행:** Swift 호스트 + WKWebView + 내장 Node 런타임을 채택한다. 원격 서버를 보여 주는 래퍼로 목표를 바꾸지 않는다.
3. **확장 구분:** 공식 에이전트 패키지의 서버 모듈은 살린다. 별도 OS 샌드박스를 요구하는 개인용 Server Extension은 v1에서 제외한다.
4. **생활 가능한 첫 버전:** 채팅·저장·파일 가져오기/내보내기·대표 에이전트·직접 만든 브라우저 확장을 실제로 사용한다.
5. **검증의 한계:** “소스에 구현돼 있음”과 “이 iPhone 앱에서 작동함”은 다르다. 다만 이를 이유로 구현을 미루지는 않는다.

## 1. 설계 근거

### 1.1 Node 서버를 유지하는 이유

**✅ Verified — 소스:** 고정한 엔진은 `2.5.0`, Node 요구 범위는 `>=24 <27`이다. 서버·클라이언트·공유 패키지를 빌드하는 구조이며, 서버는 Fastify를 사용한다. [S01][S02]

**설계 판단:** iOS 포팅의 목적은 기존 채팅과 확장 생태계를 유지하는 것이다. 서버 전체를 Rust로 옮기면 기존 라우트, 저장, 에이전트 실행, Node 의존성을 다시 구현해야 한다. 첫 버전에서는 플랫폼 의존 부분만 바꾼다.

Swift는 앱 시작, WebView, 파일 선택/공유, 앱 상태 전달을 담당한다. 필요하면 작은 Objective-C++ 브리지로 Node 라이브러리와 연결한다. 브리지 함수 이름은 실제 채택한 런타임 헤더에 맞추며, 확인하지 않은 API를 만들어 사용하지 않는다.

### 1.2 현재 저장 계층은 파일 기반이다

**✅ Verified — 소스:** `db/connection.ts`는 `createFileNativeDB()`를 사용한다. `DATA_DIR`는 앱 데이터 위치를 지정하는 경로다. [S03][S04]

**설계 판단:** v1에서 SQLite/Core Data로 저장소를 교체하지 않는다. 기존 저장 계층에 iOS 앱의 쓰기 가능한 데이터 디렉터리를 연결한다.

**주의:** 이것은 네이티브 DB 바인딩을 새로 포팅할 부담이 없다는 뜻이지, `DATA_DIR`만 바꾸면 모든 저장 문제가 해결된다는 뜻은 아니다. 파일 선택, 백업, 앱 중단 시 저장은 실제 사용 과정에서 확인한다.

### 1.3 공식 에이전트 패키지와 개인용 서버 확장은 다른 실행 경로다

| 구분 | 확인한 구현 | v1 결정 |
|---|---|---|
| 공식 에이전트 정의 | `agents.json`을 엔진의 에이전트 기능과 연결 | 우선 지원 |
| 공식 패키지 서버 기능 | 검증한 `server.mjs`를 메인 Node에서 동적 `import()` 후 `activate(context)` | 지원 대상 |
| 공식 패키지 화면 | `client.js` 및 UI 기여 지점 | 지원 대상 |
| 샌드박스 브라우저 확장 | 불투명 출처 iframe 안의 Worker | 지원 대상 |
| 전체 페이지 확장(Full-page Extension) | 승인된 JS/CSS가 마리나라 페이지 권한으로 실행 | 명시적 승인 후 지원 |
| 개인용 서버 확장(Server Personal Extension) | 자식 프로세스 + macOS Seatbelt/Linux Bubblewrap | v1 제외 |

**✅ Verified — 소스:** 공식 패키지는 `capability-module-runtime.service.ts`, 개인용 서버 확장은 `personal-extension-sandbox.ts`에 서로 다른 로더가 있다. 브라우저/전체 페이지 확장의 권한 차이는 확장 문서에 명시돼 있다. [S05][S06][S07]

**중요:** 공식 패키지의 서버 모듈이 메인 프로세스에서 실행된다는 것은 호환성에는 유리하지만, 불신 코드를 안전하게 격리한다는 뜻은 아니다. 출처·해시 검사를 유지하고, v1에서 임의의 제3자 서버 코드를 공식 패키지처럼 허용하지 않는다.

### 1.4 에이전트 파일 구성은 우선순위 판단 자료다

**✅ Verified — 고정 카탈로그의 정적 분류:** 엔진 2용 카탈로그는 39개이며, `agents.json`만 있는 패키지 23개, `agents.json + client.js` 1개, 서버·클라이언트 코드가 모두 있는 패키지 15개다. [S08][S09]

**설계 판단:** 정의 중심 패키지와 작은 서버/클라이언트 패키지부터 붙이면 엔진의 실제 확장 경로를 빨리 살릴 수 있다.

**주의:** `server.mjs`가 없어도 엔진 내부 처리기, 이미지 서비스, 외부 장치 등에 의존할 수 있다. “23개가 JSON뿐이므로 전부 자동 호환”이라고 해석하지 않는다.

### 1.5 Node 24 내장 경로는 후보이지 완성된 포트가 아니다

**✅ Verified — 후보 런타임 문서:** `fogtape/nodejs-mobile`의 `recipe` 브랜치에는 모바일 임베딩 환경과 iOS의 JIT 없는 V8, WebAssembly 대체 구현에 관한 문서가 있다. 이 문서는 단일 Node 인스턴스, 프로세스 생성 제약, 앱 내부 경로 사용도 설명한다. [S10][S11]

**⚠️ Possible — 채택 방향:** 이 포크의 고정 버전을 첫 후보로 사용한다. 채택한 라이브러리의 Node 버전, 기기 아키텍처, 배포 대상, 출처를 빌드 문서에 남긴다. 다른 더 적합한 런타임을 발견하면 이유를 짧게 적고 교체할 수 있다.

**실무상 중요한 제약:**

- 후보의 iOS WebAssembly는 제한된 JS 구현이다. `fetch()`가 된다고 `sharp`의 WASM 이미지 처리나 `quickjs-emscripten`도 된다고 볼 수 없다. 무거운 선택 기능은 우선 끄고, 핵심 기능이 필요로 할 때만 대체한다. [S02][S10]
- Node 런타임과 WKWebView는 서로 다른 실행 환경이다. 한쪽의 WebAssembly 지원을 다른 쪽에 적용하지 않는다. [S10]
- 공식 Node.js Mobile iOS 가이드는 종료된 엔진의 재시작을 지원하지 않는다고 설명한다. 후보 포크에서 별도로 입증하지 않는 한, **v1은 앱 프로세스당 Node 한 번 시작**을 전제로 한다. [S12]
- Node의 별도 실행 스레드는 UI를 막지 않기 위한 것이다. 앱을 닫은 뒤 무기한 실행하겠다는 설계가 아니다.

### 1.6 기존 Android 코드는 참고이지 그대로 이식할 호스트가 아니다

**✅ Verified — 문서:** 공식 Android 앱은 Termux 서버를 사용하는 부트스트랩 + WebView 래퍼다. [S13]

**설계 판단:** 파일 입출력과 로컬 인증의 동작은 참고하되, iOS에서는 Node와 사전 빌드한 엔진을 앱에 내장한다. Termux, Docker, `git clone`, `pnpm install`을 iPhone에 설치하는 방식으로 바꾸지 않는다.

## 2. 설계 목표

### 2.1 사용자 경험

앱을 실행하면 기기 내부 서버가 시작되고 마리나라 화면이 열린다. API 연결을 설정하고 캐릭터를 가져와 대화한다. 앱을 다시 열어도 채팅·설정·설치한 에이전트가 남아 있다. 직접 만든 브라우저 확장을 가져와 실행하고, 필요한 자료는 파일 앱으로 내보낸다.

**“별도 서버 없음”의 의미:** 마리나라 애플리케이션 서버가 iPhone 안에 있다. 모델 추론까지 오프라인으로 수행한다는 뜻은 아니다. v1의 LLM·이미지 생성은 사용자가 설정한 외부 API를 이용한다. 연결이 없어도 이미 저장된 자료는 열람할 수 있도록 한다.

### 2.2 기능 범위

| 영역 | v1 목표 | 구현 경계 |
|---|---|---|
| 대화 | Conversation, Group Conversation, Roleplay | 보내기, 스트리밍, 중지, 편집·재생성·저장 |
| 기본 게임 | 원본의 기본 Game Mode 유지 | 대형 추가 게임 패키지까지 보장하지 않음 |
| 구성 자료 | 캐릭터, 페르소나, 프리셋, 로어북, 정규식 | 기존 데이터 형식과 처리 흐름 재사용 |
| 모델 연결 | HTTP API 기반 채팅 | 실제 사용하는 연결부터; CLI/구독 도구 실행형은 제외 |
| 파일 | 캐릭터 PNG/JSON, 이미지 첨부, 채팅·설정 백업 | 파일 앱 가져오기/내보내기 및 공유 |
| 공식 에이전트 | 카탈로그 조회·설치·삭제, 대표 패키지 실행 | 업데이트는 수동; 런타임 변경은 앱 재실행 허용 |
| 개인/외부 확장 | 샌드박스 Browser, 승인된 Full-page | 원본 승인·권한·해시 검사 유지 |
| 기본 미디어 | 기존 이미지 표시·저장 | 원격 이미지 생성/TTS는 핵심 채팅 뒤에 순차 추가 |
| 복구 | 정상 재실행, 중단 표시, 재접속 | 중단된 유료 요청을 임의로 다시 보내지 않음 |

엔진의 기능을 우선 보존하되, 동작하지 않는 항목은 이유와 함께 사용 불가로 표시한다. 버튼만 숨겨 놓고 서버 경로는 계속 실행되게 두지 않는다.

### 2.3 에이전트 우선순위

**첫 연결에 사용할 대표 묶음:** 캐릭터 추적기(Character Tracker), 세계 상태(World State), 선택지(CYOA Choices), 로어북 관리(Lorebook Keeper), 서사 지휘(Narrative Director).

이 묶음으로 설정, 모델 호출, 결과 반영, 저장까지 연결한다. 모든 에이전트를 한꺼번에 켜서 사용자의 API 비용을 발생시키지 않는다. 명칭·패키지 역할은 공식 카탈로그 기준이다. [S08][S09]

**다음 호환 대상:** 정의 중심의 다른 패키지와 비홀더(Beholder)의 온라인 모델 경로. 배경·표정은 기존 이미지로 먼저 확인한다. 일러스트레이터(Illustrator), 스토리보드(Storyboard), 음악 DJ(Music DJ), 몰입형 HTML(Immersive HTML)은 추가 미디어·렌더링 요구가 있으므로 JSON 형식만으로 완료 처리하지 않는다. [S09]

**서버/클라이언트 패키지:** 틱택토(Tic-Tac-Toe) 하나를 먼저 연결한다. 이후 체스(Chess), 가위바위보(Rock-Paper-Scissors), UNO, 포커(Poker), 8볼(8-Ball Pool)을 같은 호스트로 확장한다. 여섯 개는 호환 목표이지 여섯 개의 별도 아키텍처를 만들라는 요구가 아니다. [S08]

여섯 게임 중 하나의 개별 UI 문제가 다른 채팅·확장 개발 전체를 막아서는 안 된다. 실제 동작한 패키지만 지원 목록에 적는다. 앞서 정한 넓은 호환 목표는 유지하되 **전부 완벽해야 첫 실행본을 전달할 수 있다는 조건은 두지 않는다.**

### 2.4 v1에서 하지 않는 것

| 제외 항목 | 이유 / 이후 방향 |
|---|---|
| 개인용 Server Extension | 기존 OS 샌드박스 경로를 iOS에서 그대로 쓸 수 없음. 검사 해제로 우회하지 않음 |
| Python/MLX/로컬 모델 sidecar | 외부 프로세스·모델 런타임이 필요한 별도 작업 |
| 로컬 ONNX 임베딩 | 현재 로컬 임베더는 네이티브 바인딩을 확인한다. 원격 임베딩 경로를 후속 검토 [S14] |
| Professor Mari의 셸·워크스페이스 실행 | 일반 상담/앱 지원과 OS 명령 실행을 분리; 후자는 제외 |
| Calls, 카메라·마이크 실시간 통화 | 별도 미디어 권한·오디오 수명주기 작업 |
| Haptic/Intiface 연동 | 외부 장치·서비스 경로; 단독 채팅 앱의 첫 목표 아님 [S09] |
| 멀티플레이 | 새 신뢰 경계와 네이티브 브리지 검토를 v1에 추가하지 않음 |
| Noodle·Slurp·Gacha Forge·World Maps 전체 보장 | 호스트 안정화 후 개별 패키지로 추가 |
| 엔진 자체 OTA/기기 내부 빌드 | 엔진 변경은 새 앱 빌드로 반영 |
| App Store 제출, 백그라운드 상시 서버 | 개인 기기용 개발과 별도 과제 |
| 기존 SillyTavern 확장과의 호환 계층 | 이번 대상은 Marinara 확장 형식 |

장기 기억(Long-Term Memory), 기억 알림(Memory Nag), 관계 추적(Relationship Tracker), 장비 관리(Quartermaster)는 영구 제외가 아니라 후속 우선 후보다. `server.mjs`가 있다는 이유만으로 금지하지 않는다.

## 3. 구현 설계

### 3.1 호스트와 엔진의 책임

**Swift 호스트:** 앱 시작 → 경로/설정 전달 → Node 한 번 시작 → 서버 준비 및 인증 확인 → WKWebView 표시. 파일 선택·공유·외부 링크·앱 상태 전환을 처리한다.

**내장 Node:** 기존 Fastify 라우트, 저장, 프롬프트, 모델 API, 에이전트 및 공식 패키지 서버 모듈을 담당한다.

**WKWebView:** 사전 빌드한 기존 React 화면과 브라우저 확장을 실행한다. 엔진이 같은 로컬 출처에서 화면과 API를 제공하는 구성을 우선 사용한다.

### 3.2 최소 변경 위치

아래는 **신규 파일 배치 제안**이다. 현재 upstream에 존재하는 파일 목록이 아니다.

```text
Marinara-Engine/
├── packages/                     # 기존 엔진; 필요한 플랫폼 경계만 수정
├── ios/
│   ├── MarinaraIOS.xcodeproj/
│   ├── App/                      # Swift 화면·앱 상태
│   ├── Runtime/                  # Node 호스트와 필요시 Objective-C++ 브리지
│   ├── WebView/                  # 탐색·파일 입출력 연결
│   └── README.md                 # 실제 빌드·서명·실행 방법
├── scripts/
│   └── build-ios.mjs             # 신규 제안: 실제 구현 후 명령 제공
└── docs/ios/
    ├── GOAL.md
    ├── MARINARA_IOS_HANDOFF.md
    ├── ASTRA_REQUEST.md
    └── WORKLOG.md
```

`MARINARA_IOS=1` 같은 플랫폼 표시가 필요하면 새로 도입할 수 있다. **이 이름은 기존 설정이라고 확인한 것이 아니다.** 작은 플랫폼 설정 모듈 하나로 지원 기능을 정리하고, 화면과 서버가 같은 결정을 보게 한다. 광범위한 플랫폼 프레임워크를 먼저 만들지 않는다.

### 3.3 시작 경로와 저장 경로

- 데스크톱 시작 스크립트와 프로세스 감독기를 앱에서 그대로 호출하지 않는다. iOS용 진입점이 빌드된 서버를 직접 시작하도록 연결한다.
- 앱 번들에는 빌드한 서버·클라이언트·필수 의존성을 둔다. 사용자 데이터는 번들과 분리한다.
- `Library/Application Support/Marinara`를 `DATA_DIR` 후보로 쓴다. 임시 파일과 재생성 가능한 캐시는 별도 위치를 사용한다. 경로는 iOS API에서 얻고 컨테이너 UUID를 하드코딩하지 않는다. [S11]
- 패키지 스냅샷 및 `node_modules` 연결이 기존 레이아웃에 의존하므로, 처음에는 원본 디렉터리 구조를 최대한 유지한다. 전체 서버를 단일 파일로 묶는 최적화는 뒤로 미룬다. [S05]
- 첫 버전은 `127.0.0.1`에만 바인딩한다. 포트는 우선 기존 관례인 `7860`을 후보로 사용하되 선택한 값은 한 곳에서 관리한다. 충돌 시 임의의 기존 서버를 앱 화면에 로드하지 말고 오류를 표시한다.

### 3.4 로컬 인증과 네이티브 브리지

로컬 서버라는 이유로 인증을 제거하지 않는다. 앱과 서버 사이에 설치 또는 실행 단위 비밀값으로 인증 경로를 두고, 호스트·출처·CSRF 방어를 유지한다. 기존 Android 인증 구현은 참고하되 iOS용 요구에 맞춰 적용한다. [S13]

네이티브 브리지는 파일 선택·명시적 내보내기 등 실제 필요한 동작만 노출한다. 웹 페이지에 임의의 파일 경로 읽기·셸 실행·키체인 전체 조회 API를 제공하지 않는다. iframe이나 외부 페이지가 같은 브리지 권한을 얻지 않도록 호출 출처와 프레임을 확인한다.

**Full-page 확장은 페이지 자체와 같은 실질 권한을 가진다.** 프레임 검사만으로 이 확장과 본체를 격리했다고 주장하지 않는다. 원본의 두 단계 활성화 및 정확한 코드 해시 승인을 유지한다. [S07]

API 키는 커밋·예제 설정·로그·기본 백업에 넣지 않는다. 기존 엔진의 키 저장 방식을 먼저 확인한다. 키체인(Keychain)을 추가했다면 Node 쪽 파일에도 평문 복사본을 계속 남겨 두고 “키체인 보관 완료”라고 쓰지 않는다. 키체인 전면 이행 때문에 채팅 구현을 중단할 필요는 없지만, 첫 사용본의 실제 저장 방식과 백업 제외 여부는 알려야 한다.

### 3.5 앱 재실행과 중단 처리

**v1은 Node 자동 재기동을 요구하지 않는다.** 정상 상태에서 앱이 다시 보이면 서버 상태를 확인하고 화면을 재연결한다. Node가 종료됐거나 패키지 변경에 런타임 재시작이 필요하면 저장 후 사용자가 앱을 완전히 종료하고 다시 열도록 안내한다. `node::Start()` 반복 호출이나 `process.exit()` 기반 자동 재시작을 기본 설계로 삼지 않는다. [S10][S12]

개인용으로 가장 중요한 것은 “서버가 영원히 살아 있음”이 아니라 **저장한 대화를 잃지 않고 다시 열 수 있음**이다. 백그라운드 진입 시 새로운 자동 생성은 멈추는 쪽을 기본으로 삼는다. 진행 중 응답이 끊기면 중단 상태를 표시하고, 재개 시 유료 요청을 자동 재전송하지 않는다.

Node 네이티브 충돌이 앱 프로세스 전체를 끝낼 수 있다는 점을 고려한다. 그 경우 앱 안에서 즉시 복구했다고 가정하지 말고 다음 실행에서 남은 데이터와 가능한 로그를 확인한다.

### 3.6 선택 의존성 처리

`sharp`, ONNX, Python sidecar, CLI 기반 공급자, 사용자 스크립트 도구는 핵심 채팅과 분리한다. 한 선택 기능의 import 실패 때문에 앱 전체가 부팅되지 않으면 그 경계에 지연 로딩 또는 명시적 비활성화를 둔다. [S02][S14]

PNG 캐릭터 가져오기처럼 v1 필수 경로에 이미지 처리가 필요하면 그 경로만 살린다. 작은 JS 처리나 iOS 이미지 API로 대체할 수 있지만, 캐릭터 PNG 메타데이터를 잃는 변환을 해서는 안 된다.

`quickjs-emscripten`이나 복잡한 WASM 기능을 살리기 위한 런타임 재설계는 기본 요구가 아니다. 해당 기능을 사용하는 실제 경로가 v1 필수인지 먼저 보고 결정한다.

## 4. 작업 체크내역과 진행 방식

체크박스 상세본은 `WORKLOG.md`에 있다. 아래 여섯 묶음을 GitHub 이슈 또는 작은 PR 단위로 사용한다. 아직 앱 구현 항목은 완료 처리하지 않는다.

| 작업 | 만들 것 | 그 작업을 끝냈다고 볼 기준 |
|---|---|---|
| 1. 호스트 세우기 | Xcode 프로젝트, 내장 Node, WKWebView | 앱에서 내부 HTTP 응답을 읽음 |
| 2. 실제 엔진 올리기 | iOS 진입점, 사전 빌드 자산, 플랫폼 차단 | 데모 화면이 아니라 Marinara 화면이 열림 |
| 3. 채팅과 데이터 연결 | 실제 API 채팅, 캐릭터 파일, 영구 저장, 내보내기 | 대화하고 다시 열었을 때 자료가 남음 |
| 4. 공식 에이전트 연결 | 대표 정의형 에이전트 + 틱택토 서버/클라이언트 | 설치한 기능이 결과·화면·저장에 실제 반영됨 |
| 5. 브라우저 확장 연결 | Browser 및 승인된 Full-page import/실행 | 직접 만든 작은 확장을 켜고 끌 수 있음 |
| 6. 개인용 실행본 정리 | 오류 안내, 앱 재실행, 빌드·서명 설명 | 사용자가 같은 소스로 기기에 올리고 다시 빌드 가능 |

### 최소 실행 확인

완료 조건은 다음 다섯 사용 흐름에 모은다. 별도 범용 검증 프레임워크는 요구하지 않는다.

1. **실행과 채팅:** 설치 → 엔진 화면 → API 연결 → 캐릭터 대화 → 스트리밍 중지.
2. **저장과 파일:** 캐릭터 PNG/JSON 가져오기 → 대화 → 앱 완전 종료/재실행 → 내보내기.
3. **공식 에이전트:** 대표 에이전트 설치 → 한 턴에 적용 → 틱택토 설치·실행 → 재실행 후 상태 확인.
4. **브라우저 확장:** 작은 패널/메모 확장 → 활성화·비활성화 → 승인된 Full-page UI 변경 → 변경 코드 재승인.
5. **기본 실패 대응:** 잘못된 API 키, 연결 끊김, 변조된 패키지/확장에 명확한 오류. 저장 데이터와 기존 방어를 깨지 않음.

기존 엔진에 관련 테스트가 있으면 해당 부분만 재사용한다. 문서·주석만 바꿨을 때 전체 회귀 테스트를 돌릴 필요는 없다. 공통 호스트 하나를 고친 뒤 각 게임에 동일한 긴 테스트 절차를 반복해서 만들지 않는다.

### 첫 전달 단위

첫 PR은 전체 v1이 아니라 **1번 호스트 + 가능한 범위의 2번 실제 엔진 부팅**이다. 활성 Goal에서는 이를 중간 결과로 전달하고 다음 구현을 계속한다. 첫 PR 생성만으로 전체 Goal을 완료하지 않는다. 작업을 착수했다면 설계 문서만 늘리지 말고 코드와 실행 경로를 남긴다. Xcode 또는 실제 기기가 없는 환경에서는 소스와 준비 스크립트를 만들고, 실행하지 못한 명령만 정확히 적는다. 실행하지 않은 결과를 성공이라고 쓰지 않는다.

## 5. 이후 단계

### v1 다음: 사용 가치가 큰 기능부터

첫 후속 묶음은 남은 정의형 에이전트와 여섯 게임의 호환 확대, Beholder의 온라인 경로, 원격 이미지 생성과 TTS다. 모두 기존 호스트를 재사용한다.

다음으로 Memory Nag·Relationship Tracker·Quartermaster를 본다. Long-Term Memory는 원격 임베딩 연결을 우선 고려한다. 현재 엔진에는 설정된 임베딩 호스트를 제공하는 기능이 있으므로, 로컬 ONNX 포팅만이 유일한 길이라고 전제하지 않는다. [S15]

### 그다음: 큰 앱 기능과 유지보수

Noodle·Slurp·Gacha Forge·World Maps는 하나씩 실제 사용하는 흐름에 맞춰 추가한다. 로딩 속도, 큰 채팅, 이미지 메모리, 키체인 통합, 작은 배포 용량은 실제 병목을 보고 개선한다.

상위 원본(upstream) 업데이트는 원본 커밋과 포팅 변경을 구분해 반영한다. 각 버전마다 최소 다섯 사용 흐름을 필요한 범위에서 다시 확인한다. 처음부터 모든 원본 변경에 자동 대응하는 패치 시스템을 만들지 않는다.

### 별도 과제

개인용 Server Extension의 iOS 실행기는 별도 설계다. OS 샌드박스를 제거하고 같은 기능이라고 부르는 방식은 쓰지 않는다. 실시간 통화, 로컬 모델, 멀티플레이, App Store 배포도 각각 별도 범위로 결정한다.

## 6. 아스트라에게 적용할 작업 지침

- 이 문서를 **구현 지시**로 받아들인다. 기획서를 다시 작성하는 작업으로 바꾸지 않는다.
- 기존 앱 추천이나 원격 서버/PWA 설치 안내로 목표를 대체하지 않는다. 기존 프로젝트는 코드·설계 참고용이다.
- 작업 저장소의 기존 지침과 변경 사항을 먼저 읽고, 사용자의 작업을 덮어쓰지 않는다. 원본 공식 저장소에 직접 푸시하는 계획은 세우지 않는다.
- 시작 기준은 아래 고정 커밋이다. 더 최근 버전을 쓰려면 이유와 바뀐 기준만 기록한다. 전체 저장소를 매번 다시 감사하지 않는다.
- 작게 구현하고 실제 실행 경로를 이어 붙인다. 막힌 기능은 경계에서 분리하고 나머지 코드를 진행한다.
- 보안 검사를 없애거나 TLS 검증을 끄는 방식으로 “작동”시키지 않는다. 불신 확장을 신뢰 코드로 승격하지 않는다.
- 사용자의 실제 데이터 대신 작은 테스트 프로필을 쓴다. API 키·서명 인증서·프로비저닝 자료를 커밋하지 않는다. 유료 API 호출은 사용자가 허용한 연결과 범위에서만 한다.
- 새로운 플랫폼 설정, 스크립트, 브리지 API는 제안과 실제 구현을 구분한다. 동작하는 척하는 스텁을 완료 처리하지 않는다.
- 결과 보고는 **바꾼 것 / 실제로 실행한 것 / 막힌 것 / 다음 코드 작업**만 간단히 쓴다.
- 광범위한 호환성을 입증하느라 초기 실행본 전달을 미루지 않는다. 실제 되는 것과 안 되는 것을 분명히 알려 준다.

## 7. 두 독립 구현의 비교 기준

같은 엔진·Agents 기준, 같은 캐릭터 카드, 같은 프리셋·모델 설정을 사용한다. 각 구현에는 별도 앱 식별자와 별도 테스트 데이터를 사용해 서로의 데이터를 덮어쓰지 않는다.

비교는 점수표보다 다음 질문이면 충분하다.

| 비교 항목 | 볼 내용 |
|---|---|
| 만들기 쉬운가 | 깨끗한 체크아웃에서 빌드까지 필요한 수동 작업 |
| 실제로 쓰이는가 | 채팅·캐릭터 가져오기·확장 실행의 성공 여부 |
| 자료가 남는가 | 재실행 후 채팅·설정·패키지·확장 상태 |
| 원본을 얼마나 바꿨는가 | upstream 수정 위치와 유지보수 부담 |
| 어디에서 막히는가 | 런타임, 이미지, WASM, 파일, 패키지 등 실제 오류 |
| 체감이 어떤가 | 첫 화면, 스크롤, 입력, 발열·메모리 문제; 필요할 때만 수치 기록 |

모델 응답은 동일 조건에서도 달라질 수 있으므로 문장 일치로 포팅 성공을 판정하지 않는다. 구조화된 에이전트 결과 반영, 요청 흐름, 저장된 상태를 비교한다. 성능 수치는 같은 기기·빌드 종류·데이터에서 측정한 경우에만 비교한다.

## 9. 착수 시 최종 지시

**첫 작업은 Xcode 호스트에 Node를 넣고 실제 Marinara가 열리게 하는 것이다. 그다음 채팅과 저장을 연결하고, 에이전트 하나와 브라우저 확장 하나를 붙인다.**

이 순서를 지키되 거대한 사전 검증을 통과해야만 다음 코드를 쓸 수 있게 만들지 않는다. 부팅이 막히면 필요한 의존성 경계부터 고치고, 고급 기능 하나가 막히면 그 기능만 후속으로 남긴다. 결과는 실제로 작성한 코드와 실행한 범위로 설명한다.
